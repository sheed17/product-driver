IDENTIFIED RISKS:

  [P0 cross_tenant] A supervisor of tenant A releases tenant B's operation because the release path scopes by role but not by tenant, or trusts a caller-supplied tenant field instead of the operation's owning tenant.  (covered by S3)
  [P1 missing_data] A refusal returns an error to the caller but writes nothing to audit_events/security_events, so denied attempts leave no evidence (silent denial).  (covered by S8)
  [P0 malformed_input] A request with no role, an unknown role, or a missing actor is treated as authorized (fail-open) instead of refused, because absence is coerced to a permissive default.  (covered by S4)
  [P1 idempotency] Re-issuing an identical release for an already-released operation performs or records the release twice, so a retried/duplicated tap double-releases.  (covered by S5)
  [P2 restart_recovery] The refusal record is held only in memory or in a per-request kernel and is lost on restart, so the audit trail cannot answer 'who was denied' after a crash.  (covered by S7)
  [P1 concurrency] A supervisor request and a non-supervisor request race on the same operation; the loser's effect still lands or both succeed, breaking the single-releaser invariant.  (covered by S6)
